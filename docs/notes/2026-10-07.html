01

なぜテストを書くか

ここ数日で、Jev の判定の仕組みを何度も作り直した（4 択 → はい/いいえ 2 問 → 3 問、掛け算 → 低い方、いつもの場所のルール…）。直すたびに手で全部を確かめるのは大変で、見落としも出る。

テスト = 「こうなるはず」をコードで書いておくこと。あとで何かを直しても、yarn test を 1 回打てば、前に決めたルールが壊れていないかがすぐ分かる。

02

設定（playwright.config.ts）

2 つのグループ
unit（tests/unit）と e2e（tests/e2e）。Playwright はブラウザのテストの道具だが、ふつうの計算のテストにも使えるので、道具を 1 つにそろえた
テスト用のサーバー
e2e のときは Playwright が自分で next dev --port 3100 を起動する。yarn dev（3000）と同時に動かせる
本物に触らない
テスト用のサーバーにはダミーの Supabase の接続先を渡し、Jev のキーも空にする。テストで本物のデータを消したり、クレジットを使ったりしない
ブラウザ
最初の 1 回だけ yarn playwright install chromium。Firefox などは使わないので chromium だけ入れる

計算のテスト（19 本）

ファイル確かめていること
decide.spec.tsJev の確率と泊数から、日常・おでかけ・日帰り・帰省・旅行に正しく分かれる。確かさは「掛け算」ではなく「低い方」
sample-timeline.spec.ts架空のタイムラインで：37 回の外出に分かれる／15 府県＋韓国／北海道 3 泊・帰省 4 泊／通学 24 日は Jev なしで日常／保存する数字に座標が入らない
jev-state.spec.tsJev に渡す中身が日本時間の日付・曜日・時刻になっている。年をまたぐ年末年始も見つけられる
friends-and-review.spec.ts友達との比較（どちらも / 自分だけ / 友達だけ）、フレンドコード、正解率と確率の当てはまりの計算
trip-schema.spec.ts手入力の旅：未来の日付、帰った日が前、日帰りなのに日付が違う、などを弾く

「保存する数字に座標が入らない」のように、守りたい約束（プライバシー）もテストにできる。誰かが座標を保存するように変えたら、テストが落ちて気づける。

07

理解度チェック

  1. テストを書いておくと、どんなときに助かる？

    答えを見る

    あとで仕組みを直したとき。yarn test を 1 回打てば、前に決めたルール（判定の流れ・座標を保存しない など）が壊れていないかがすぐ分かる。手で全部確かめる必要がない。

  2. 画面のテストのサーバーに、本物ではなくダミーの Supabase の接続先を渡しているのはなぜ？

    答えを見る

    テストで本物のデータを読んだり消したりしないため。また、テストの結果が DB の中身によって変わらないようにするため。

  3. 計算のテスト（unit）が画面のテスト（e2e）より速いのはなぜ？

    答えを見る

    サーバーもブラウザも起動せず、関数を呼んで結果を比べるだけだから。

  4. 「ログインしていないと入れない」テストを 6 ページぶん、1 つの for 文で作れたのはなぜ？

    答えを見る

    どのページも「開く → トップページに戻される → ログインボタンが見える」という同じ確かめ方だから。違うのはページの URL だけなので、URL の一覧を回して同じテストを作った。

  5. テストの中で、時刻を startsWith("2025-08-10") で比べたら合わなかった。なぜ？

    答えを見る

    時刻が UTC で保存されていたから。日本時間 8/10 の朝 8 時は UTC では 8/9 の 23 時なので、文字列の先頭が 8/9 になる。日本時間の日付に直してから比べる。
