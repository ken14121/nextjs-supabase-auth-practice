02

db push が止まった

家のパソコンで yarn supabase db push を実行すると、「データベースにはあるのに、手元のフォルダに無い変更がある」と止まり、supabase migration repair（--status reverted）を勧められた。

本当の原因
手元で database.types.ts が書き換わっていて git pull が止まり、コードが古いままだった。データベースには、別のパソコンから 10/14〜10/15 の変更を入れてあった
やらなかったこと
勧められた migration repair。実行すると、入れた変更の記録が「取り消し」の扱いになってしまう
直し方
git stash で手元の書き換えをよけてから git pull。手元を最新にしてから db push し直す
エラーが勧めるコマンドを、そのまま実行しない。まず「何がずれているのか」を確かめる。今回はデータベースではなく、手元のコードが古いだけだった。
03

環境変数と、キーの守り方

名前ブラウザに届くかメモ
NEXT_PUBLIC_SUPABASE_URL届く公開してよい値
NEXT_PUBLIC_SUPABASE_PUBLISHABLE_KEY届く公開用のキー。sb_secret_ や service_role は絶対に入れない
JEV_API_KEY届かないNEXT_PUBLIC_ が付いていないので、サーバーの中だけで読める
JEV_OWNER_USER_IDS届かない自分の UID 1 つだけ。空ならだれも Jev を使わない
ENABLE_EXPERIMENTAL_COREPACK―Yarn 4 を使うため。値は 1
  • Jev のコードの先頭には import "server-only" があり、ブラウザ用のコードから読み込むとビルドで止まる
  • Vercel の「Optional Integrations」にある Supabase の「Add」は押さない（新しい Supabase のプロジェクトが別にできてしまう）
  • Vercel のプロジェクトにほかの人をメンバーとして招待しない（環境変数の画面でキーが見えてしまう）
04

Google のログインを本番に

ブランディング
ホームページに公開した URL、プライバシーポリシーに /privacy を入れた。ロゴは上げない（上げると Google の審査が必要になる）
承認済みドメイン
vercel.app だけでは通らず、nextjs-supabase-auth-practice.vercel.app まで書く必要があった
対象
公開ステータスを「本番環境」に。名前とメールアドレスだけを使うので、ユーザー数の上限（100 人）はかからない

vercel.app はたくさんの人のサイトが共有しているドメイン（Public Suffix List に入っている）なので、Google はその下の自分のサイトの名前までを 1 つのドメインとして扱う。

06

理解度チェック

  1. JEV_API_KEY がブラウザに届かないのはなぜ？

    答えを見る

    Next.js は NEXT_PUBLIC_ で始まる環境変数だけをブラウザ用のコードに入れるから。さらに server-only で、うっかりブラウザ用のコードから読み込むとビルドが止まる。

  2. db push で勧められた migration repair を実行しなかったのはなぜ？

    答えを見る

    ずれていたのはデータベースではなく手元のコード（古いまま）だったから。repair すると、正しく入っている変更の記録を「取り消し」にしてしまう。

  3. Google の承認済みドメインに vercel.app だけでは足りなかったのはなぜ？

    答えを見る

    vercel.app はみんなで共有しているドメインなので、自分のサイトの名前（nextjs-supabase-auth-practice.vercel.app）までが 1 つのドメインとして扱われるから。

  4. 公開したあとに、ページの JavaScript の中を検索したのはなぜ？

    答えを見る

    設定のまちがいで秘密のキーがブラウザに送られていないかを、実際に配られているファイルで確かめるため。コードを読むだけでなく、外から見える結果で確かめた。
