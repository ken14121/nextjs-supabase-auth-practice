Step 4：テーブル設計

コードを書く前に、何をどうしまうかを決めた。決めたこと：友達はフレンドコード（8 文字）で探す。友達には「行った県・国と日付」まで見せる。

テーブル主な列何に使う
profilesdisplay_name、friend_code友達を探すときの名札。初めてログインしたときにトリガーで自動作成
outings開始・終了日時、nights、distance_km、main_transport、label（Jev の判定）、memo外出 1 回ぶん（家を出てから戻るまで）
visited_regionsregion_code（JP-13 / US）、outing_id、visited_on地図の塗りつぶし・制覇率
friendshipsrequester_id、addressee_id、status友達申請（申請中 / 承認済み）
地域コード
国際規格 ISO 3166。都道府県は JP-01〜JP-47（東京都は JP-13）、国は 2 文字（アメリカは US）。形の違う値は check 制約で入れられない
制約
終了は開始より後、泊数は 0 以上、同じ人の同じ開始時刻の外出は 1 件だけ、A→B と B→A の申請は両方作れない、など。DB 側で守れるルールは DB に書く
02

RLS と権限

仕組み役割このアプリでは
RLS（ポリシー）「どの行を」読み書きできるかoutings・visited_regions は本人だけ。申請は関係者だけ見られ、承認できるのは申請された側だけ
grant（権限）「どのテーブル・どの列を」使えるか自動公開を OFF にしたので、テーブルごとに付けた。update (status) のように列を絞ると、それ以外の列は書き換えられない
security definer 関数テーブルの持ち主の権限で動く関数友達の訪問地を返す関数の中で「承認済みの友達か」を確かめ、県・国と日付だけを返す。日常・未判定の外出は含めない

auth.uid() は今ログインしている人の ID。(select auth.uid()) と書くと行ごとではなく 1 回だけ計算されて速い。反映前に、3 人のユーザーを想定した 20 項目のテストで狙いどおりに動くことを確かめた。

Supabase CLI とマイグレーション

SQL を書くsupabase/migrations/ → yarn supabase db push本番の DB に反映 → yarn gen:typesテーブルの形から型を生成 → createClient<Database>列名の間違いが赤線に
マイグレーション
DB の変更を SQL ファイルとしてリポジトリに残す方法。作り直せるし、何をいつ変えたかの履歴になる。画面でテーブルを作るとこれが残らない
準備したこと
DB パスワードを強いものにリセット（Database → Settings）→ yarn add -D supabase → init → login → link
型の効果
.select("friend_codeXX") のように存在しない列を書くと、その場で VS Code が教えてくれる
04

Step 5：Timeline.json の取り込みの仕組み

  1. 1
    ブラウザ（/import）

    ファイルを選ぶ。lib/timeline/parse.ts が iPhone・Android の両形式を Zod で読み、滞在と移動だけを取り出す。軌跡は捨てて 7.8 MB → 1.2 MB

  2. 2
    SUPABASE STORAGE

    timelines バケットの自分のフォルダ（ユーザー ID/〇〇.json）に置く。他人のフォルダには RLS で置けない

  3. 3
    SERVER ACTION（app/import/actions.ts）

    ファイルを読み、ブラウザから来たものは信用せず Zod でもう一度チェック

  4. 4
    LIB/TIMELINE/OUTINGS.TS ＋ LIB/GEO/REGIONS.TS

    外出に区切り、立ち寄った地点の緯度経度から都道府県・国を判定

  5. 5
    DB

    outings に upsert（取り込み直しても重複しない。Jev の判定やメモは消えない）、visited_regions を入れ直す

  6. 6
    後片付け

    元ファイルを Storage から削除（成功しても失敗しても）。位置情報の生データは残さない

Storage を通す理由
Server Action に直接送れるのは初期設定で 1 MB まで。大きなファイルは Storage に置いてサーバーが取りに行く
県・国の判定
都道府県の境界（地球地図日本）と国の境界（Natural Earth）の中に点が入っているかを調べる。境界データは粗いので、海沿いや空港などどこにも入らない点は 15 km 以内の一番近い地域にする（羽田・関西空港もこれで正しく判定）
出典表示
境界データには出典の明記が必要なので、README とマイページに書いた
05

外出の区切り方

ルール理由
自宅は「Home」と記録された場所。なければ一番長く滞在した場所Android や記録の少ないファイルでも動くように
自宅から 1.5 km 以内の地点は記録しない自宅の位置を残さない・友達に見せない。近所の外出は数えない
自宅の滞在、または自宅の周りに戻ってきた移動で外出を締めくくる帰宅後に自宅での滞在が記録されない日があり、翌日の外出とつながって「泊まり」に見えていたため（今日直した）
泊数は日本時間 3:00 をまたいだ回数22 時に出て 1 時に帰るのは 0 泊、2 日後の夜に帰るのは 2 泊
主な移動手段は、一番長い距離を移動した手段駅まで歩いて電車に乗った日を「電車」にするため

残る「東京に 1 泊」は、学校に泊まり込んで始発で帰った日。データとしては正しいが、旅行ではない。Step 7 で Jev に「その行き先に過去どれくらい行っているか」も渡して「日常」と判定させる。よく行く場所（学校・バイト先）を登録して除外する案もやりたいことリストへ。

つまずいたことと学び

起きたこと原因対処
DB パスワードの場所が分からないProject Settings ではなく Database の設定にあるDatabase → Configuration → Settings → Reset database password
supabase init で「ファイルが既にある」前に一度実行していたinit は 1 回で十分なので飛ばした
生成した型ファイルが lint エラーのまま push されたSupabase が生成するコードと Biome の書き方の違いgen:types の最後に biome format を付けて、生成と同時に整えるようにした
PowerShell で > を使うと型ファイルが壊れるWindows PowerShell は UTF-16 で書き出すpackage.json のスクリプト経由で実行（UTF-8 になる）
「東京に 1 泊」が多すぎた帰宅後の自宅での滞在が記録されない日がある自宅の周りに戻る移動でも外出を区切るようにした
07

理解度チェック

  1. テーブルを作ったのに permission denied になった。何を確認する？

    答えを見る

    grant（権限）の付け忘れ。このプロジェクトは新しいテーブルを自動公開しない設定なので、authenticated へ使う操作の権限を付ける。

  2. RLS があるのに、友達の訪問地を関数（security definer）で返しているのはなぜ？

    答えを見る

    テーブルは本人だけに閉じたまま、「承認済みの友達か」を確かめたうえで、県・国と日付という必要な列だけを渡すため。RLS だけだと行ごとの許可はできても、「一部の列だけ」「日常は除く」といった見せ方がしにくい。

  3. Timeline.json をブラウザから直接 Server Action に送らないのはなぜ？

    答えを見る

    Server Action に送れるのは初期設定で 1 MB まで。大きなファイルは Storage に置き、サーバーがそこから読む。

  4. ブラウザでチェック済みなのに、サーバーでも Zod でチェックするのはなぜ？

    答えを見る

    ブラウザから来たデータは書き換えられている可能性があり、信用できないから。

  5. 同じファイルを 2 回取り込んでも外出が重複しないのはなぜ？

    答えを見る

    outings に「同じ人・同じ開始時刻は 1 件」の制約があり、upsert で上書きしているから。訪問地はその外出の分を消してから入れ直す。

  6. DB に自宅の位置が残らないのはなぜ？

    答えを見る

    自宅から 1.5 km 以内の地点は立ち寄り先に入れず、DB には県・国と日付だけを保存し、元ファイルも取り込み後に削除しているから。
