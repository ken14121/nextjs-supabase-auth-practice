01

友達申請の流れ

  1. 1
    A さん（/friends）

    B さんのフレンドコードを入れて「申請」。フォームは react-hook-form ＋ Zod（8 文字の英数字か。大文字や前後の空白は直してから調べる）

  2. 2
    SERVER ACTION（app/friends/actions.ts）

    find_profile_by_friend_code で相手を探す（自分のコードでは見つからない）。すでに友達・申請済みなら、そう伝える。B さんから申請が届いていたら、そのまま承認する

  3. 3
    DB（friendships）

    requester_id = A, addressee_id = B, status = pending の行ができる。A→B と B→A の 2 行は一意インデックスで作れない

  4. 4
    B さん（/friends）

    「届いた申請」に A さんが出る。承認すると status = accepted。承認できるのは申請された側（addressee）だけ ← RLS が守る

  5. 5
    比べるページ

    友達の訪問地は get_friend_visited_regions 関数から。中で「承認済みの友達か」を確かめ、県・国と日付だけを返す

「断る」「取り消す」「友達をやめる」は、どれも 2 人の行を消すだけ。だから Server Action は 1 つ（removeFriendship）にまとめた。

02

比べるページ

比べ方
自分の県・国の集合と、友達の集合を比べて 3 つに分ける（lib/friends/compare.ts）。国で比べるときは、都道府県をまとめて「日本」にする
友達側の範囲
旅行・帰省・日帰りと判定された外出だけ。日常の外出と、まだ判定していない外出は共有しない（家のまわりや毎日の行動を見せないため）
今の状態
タイムラインから取り込んだ外出は Jev で判定する前なので「未判定」。今は手入力した旅だけが友達に見える（メイン垢の比較が 7 県だったのはこのため）。来週 Step 7 で解決する
見つからないとき
友達でない人の ID を URL に入れても、notFound() で「ページが無い」扱いにする。ID の形（UUID）も Zod で確かめる

自分だけ　友達だけ　どちらも　—— 色覚の違い（赤緑など）があっても見分けられるかを、ツールで計算して確かめた

06

理解度チェック

  1. 申請した側（A さん）が、自分で status を accepted に書き換えられないのはなぜ？

    答えを見る

    friendships の更新の RLS が「addressee_id = 自分 の行だけ」になっているから。A さんが更新しようとしても 0 行しか変わらない。アプリのコードではなく、DB 側で守っている。

  2. A さんが B さんに申請中のとき、B さんが A さんのコードで申請するとどうなる？

    答えを見る

    Server Action が「相手から申請が届いている」ことに気づいて、そのまま承認する（2 人はすぐ友達になる）。B→A の行を新しく作ろうとしても、一意インデックスで弾かれる。

  3. 友達の訪問地を、visited_regions テーブルから直接 select しないのはなぜ？

    答えを見る

    テーブルは RLS で本人しか読めないから。友達向けには security definer の関数を通し、「承認済みの友達か」を確かめてから、県・国と日付だけを、日常を除いて返す。

  4. 友達でない人の比較ページの URL を直接開いたら、何が表示される？

    答えを見る

    「ページが見つかりません」（notFound()）。もし画面が出てしまっても、関数が友達かどうかを確かめるので、相手の訪問地は 0 件しか返らない（二重に守っている）。

  5. 比べる地図で、色に加えてグループごとの一覧（文字）も出しているのはなぜ？

    答えを見る

    色の見え方は人によって違い、白い背景だと見えにくい色もあるから。色だけで意味を伝えない。

  6. 別の PC で git pull したら、次に何をする？ その理由は？

    答えを見る

    yarn install。package.json に新しい部品が増えていても、node_modules（実際の部品）は PC ごとに入れ直す必要があるから。
