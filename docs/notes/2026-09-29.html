Step 3：Google ログインの設定（画面操作）

3 つのサービスを「戻り先の確認 → 許可証の発行 → 許可証の登録」の順でつないだ。

どこで何をしたか意味
SupabaseGoogle プロバイダの Callback URL をコピーGoogle でのログインが終わったあとの Supabase の受付窓口（…supabase.co/auth/v1/callback）
Google CloudGoogle Auth Platform で同意画面を作成（外部・テスト中）、テストユーザーに自分を追加テスト中は登録した人しかログインできない。友人に試してもらうときもここに追加する
Google CloudOAuth クライアント（ウェブ アプリケーション）を作成。JavaScript 生成元に http://localhost:3000、リダイレクト URI に Supabase の Callback URL許可証。クライアント ID は公開されても大丈夫、シークレットは秘密
SupabaseGoogle プロバイダを ON にして ID とシークレットを登録Supabase が Google と話せるようになる
SupabaseURL Configuration：Site URL と Redirect URLs に http://localhost:3000ログイン後に「アプリのどこへ戻してよいか」の許可リスト
手元の PC.env.local に URL と publishable key を記入NEXT_PUBLIC_ 付きはブラウザに渡っても良い値。.env.local はコミットしない
03

ログインの流れ

  1. 1
    ボタン → APP/AUTH/ACTIONS.TS

    Server Action が Supabase に「Google でログインしたい。終わったら /auth/callback に戻して」と頼み、Google のログイン画面の URL へ移動。まだ未ログイン

  2. 2
    GOOGLE

    本人確認して許可。Supabase 経由で、アプリに一時的な code（引換券）付きで戻す

  3. 3
    APP/AUTH/CALLBACK/ROUTE.TS

    code をトークンに交換し、Cookie に保存。ここでログイン完了。失敗したら /?error=login_failed

  4. 4
    PROXY.TS（毎回・入口）

    Cookie のトークンを確かめ、期限切れなら更新。未ログインなら /dashboard から追い返す

  5. 5
    APP/DASHBOARD/PAGE.TSX

    ページ側でももう一度ログインを確認してから、名前とメールを表示

自分の言葉で：「Google でログイン」を押すと Google で本人確認が行われ、/auth/callback に一時的な code が届く。callback で code をトークンと交換して Cookie に保存した時点でログイン完了。以降はページを開くたびに proxy が Cookie のトークンを確かめ（期限切れなら更新、未ログインなら追い返す）、マイページ側でももう一度確認してから名前を表示する。

コードの読み方

ファイル役割読んで分かったこと
app/auth/actions.tsログイン・ログアウトの Server Action"use server" で中身はサーバーで動く。<form action={関数}> で、onClick を書かずにボタンから呼べる。origin はヘッダーから自動で取る
app/auth/callback/route.tsGoogle から戻ってきたときの受け口route.ts は画面を返さず処理だけする Route Handler。関数名 GET は「URL を開いたとき」。exchangeCodeForSession でログイン完了
proxy.ts入口。Next.js 16 で毎回呼ばれる旧 middleware.ts。matcher で画像や _next/static を除外
lib/supabase/proxy.tsセッション更新の本体新しい Cookie を request（このあと動くページ用）と response（ブラウザ用）の両方に書く。片方だけだと「たまにログアウト扱いになり、リロードで直る」バグになる。getClaims() が署名確認と更新をする
app/dashboard/page.tsxマイページ（Server Component）proxy だけに頼らず、ページでも getClaims() で確認。redirect() の後は claims が必ずあると TypeScript も分かる。?. と ?? で名前がなくても壊れない
lib/supabase/server.ts / client.ts / env.tsSupabase の窓口と接続情報サーバー用とブラウザ用で作り方が違う。Server Component からは Cookie を書けないので try/catch で無視し、更新は proxy に任せる

PKCE（code を挟む理由）

URL はブラウザの履歴やログに残りやすい。トークンを直接 URL に載せると漏れる危険があるので、短命・使い捨ての code だけを URL で渡し、本物のトークンはサーバー同士のやり取りで受け取る。@supabase/ssr が自動でやってくれている。

05

Cookie の話

Cookie とは
ブラウザがサイトごとに保存する小さなメモ。そのサイトにアクセスするたびに自動で送られる。イベント会場の入場リストバンドのようなもの
受け渡し
サーバーが Set-Cookie で渡し、ブラウザは以降 Cookie ヘッダーで毎回送る
主な属性
Expires（期限）／ Secure（HTTPS のときだけ）／ HttpOnly（JavaScript から読めない）／ SameSite（他サイトからの送信を防ぐ）
このアプリの Cookie
sb-jhxnynvousgjixwzcyte-auth-token。中身は アクセストークン（JWT。誰か・期限が書かれた通行証。Supabase の電子署名付きで改ざんできない。1 時間くらいで切れる）と リフレッシュトークン（新しい通行証との引換券）
サーバーだと安全な理由
① NEXT_PUBLIC_ なしの環境変数（後で使う Jev の API キーなど）はブラウザに届かない ② サーバーで署名を確かめてから画面を作れる ③ Cookie を書き換えられるのはサーバー側だけ
注意
Supabase の Cookie はブラウザ側のライブラリも読むので HttpOnly ではない。悪意のあるスクリプト（XSS）を混ぜないことが大事。Cookie の値は人に見せない（持っている人があなたとしてログインできる）
試せること
F12 → Application → Cookies → http://localhost:3000 で見える。消して再読み込みするとログアウト状態になる

07

理解度チェック

コードを読みながら答えた問題。まず自分で答えてから「答えを見る」を開く。

  1. signInWithOAuth を呼んだ直後、ユーザーはもうログインしている？

    答えを見る

    していない。Google のログイン画面の URL を用意しただけ。ログイン完了は callback で code を交換したとき。

  2. redirectTo を書かなかったら、どこに戻ってくる？

    答えを見る

    Supabase の Site URL（http://localhost:3000）。ただしトップに ?code=… が付くだけで、交換する処理がないのでログインにならない。

  3. /auth/callback?code=適当な文字 を開いたら？

    答えを見る

    交換に失敗して /?error=login_failed に戻され、赤いエラー文が出る。

  4. ログイン成功の直後、Cookie に何が増える？

    答えを見る

    sb-…-auth-token。中身はアクセストークンとリフレッシュトークン。

  5. PROTECTED_PATHS に "/settings" を足したら？

    答えを見る

    /settings と /settings/… が、未ログインだとトップに戻されるようになる。ページ側の確認も別に書く。

  6. setAll で request.cookies に書き忘れたら？

    答えを見る

    トークンの期限が切れたタイミングだけ、ページが古いトークンを読んで「未ログイン」と判断する。リロードすると直る「たまに起きる」バグになる。

  7. 画像ファイルを開くとき、proxy は動く？

    答えを見る

    動かない。matcher で画像や _next/static を除外している。誰が見ても同じなので確認は不要で、毎回動くと遅くなるだけ。
