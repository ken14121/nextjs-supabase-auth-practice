01

Jev の使い方の調べ方

困ったこと
Jev は出たばかりで、AI（Claude Code）も正しい使い方を知らない。公式ドキュメントのサイトも開けなかった
やったこと
npm に公開されている公式 SDK（@typesafe-ai/sdk）の README と型定義（.d.ts）を読んだ。型定義には、関数の引数・返り値・エラーの種類がすべて書いてあるので、ドキュメントの代わりになる
使い方
new TypeSafeClient({ apiKey }) → client.systemOne({ state, questions })。質問は noul()（はい / いいえ）・choice()（選択）・score()（点数）で作る
キーの守り方
呼び出すファイルの先頭に import "server-only"。ブラウザ用のコードから読み込むとビルドエラーになるので、API キーがブラウザに漏れない
返ってきた答え
SDK は答えの形を確かめないので、Zod で「確率が 0〜1 の数か」を確かめてから使う（外から来たデータは信用しない）
02

判定の流れ

いつもの場所だけ・泊まりなし？（コード）──はい──→ 日常（Jev を使わない）
   │いいえ
日常か？（Jev）──はい──→ 日常
   │いいえ
泊まった？（コード）──いいえ──→ 遠くへの日帰り旅行か？（Jev）──はい──→ 日帰り / いいえ → おでかけ
   │はい
帰省か？（Jev）──はい──→ 帰省 / いいえ → 旅行
Jev に渡す材料
出発・帰宅の日時と曜日、泊数、距離、移動手段、行った県と「これまでに行った日数」、住んでいる県、時期（年末年始・GW・お盆）、いつもの場所 / ふだん行かない場所にいた時間、自宅から一番遠い地点
分担
数えられることはコード、判断は Jev。Jev は計算が苦手なので、数字はすべて計算してから渡す
3 つの質問
1 回の通信でまとめて送れて、Jev の中で同時に判定されるので、1 つ聞くのとほぼ同じ速さ・回数

記事から学んだこと

知ったことアプリをどう変えたか
結果の分からないサイコロの目を Choice（選択）で聞くと、400 回すべて 1 つめを選び、確率も 83% と出た（本来 1/6）。Noul（はい / いいえ）では 19% と、1/6 に近かった4 択で聞くのをやめ、「はい / いいえ」の質問に分けた。並び順で答えが偏るのを避けるため
Jev が「はい」と 0.7〜0.9 で答えても、難しい問題では半分くらいしか当たらない（ウミガメのスープの検証）確率の数字は画面に出さず、70% 未満に「要確認」と出すことにだけ使う
（自分で気づいたこと）2 つの確率を掛け算すると、はっきりした旅行でも 0.85 × 0.8 = 0.68 になる2 つのうち低い方を使うように直した
04

いつもの場所と、ふだん行かない場所

都道府県だけだと、「東京の学校に行った日」と「渋谷に遊びに行った日」がどちらも「東京都（300 日）」に見えて区別できなかった。

見つけ方
取り込みのときに、タイムライン全体から「その地点の 500m 以内に何日行ったか」を数える。10 日以上 = いつもの場所、4〜9 日 = ときどき、3 日以下 = ふだん行かない場所。学校を自分で登録しなくても見つかる
速くする工夫
地図を約 500m 四方のマスに分け、同じマスとまわり 8 マスの地点とだけ比べる（全部どうしで比べると遅い）
保存するもの
外出ごとの滞在時間と自宅からの距離だけ（outings.features）。座標は保存しない
おでかけ
近場で遊ぶ・買い物・食事。旅の一覧と友達への共有には入れない

Jev の正解率を測る（/outings/review）

Jev の答えを残す
本人が直すと元の答えが消えてしまうので、jev_label・jev_p_daily などの列に Jev の答えを残す
「合ってる」ボタン
直したものだけでなく、合っていたものも記録しないと正解率が計算できない
でたらめに選ぶ
要確認だけを見ると正解率が低く出てしまう（偏り）。ID から決まる、でたらめだが毎回同じ順で 20 件選ぶ
出す表
正解率 ／ 要確認あり・なしの正解率 ／ Jev の答え × 本人の答え（取り違えやすい種類が分かる）／ 確率の当てはまり（「日常の確率 80〜100%」と言ったうち、実際に日常だった割合）
06

クレジットの扱い

Zendash から借りている API キーなので、使いすぎないようにした。

  • 判定済みの外出は二度と送らない。1 回のボタンで 20 件まで、同時に 4 件ずつ
  • いつもの場所だけの日はコードで日常にする（サンプルでは 37 件中 24 件が Jev なしで決まった）
  • 判定のあとに「Jev に ○ 回送信・約 ○ トークン」を表示する
  • 確かめる・選び直すはクレジットを使わない
  • 「残りをすべて判定」は、20 件の結果と使った量を見て、ゆうへいさんに確認してから

起きたこと原因対処
git pull が「Your local changes … would be overwritten」で止まった前に yarn gen:types をして、型ファイルが手元で変わっていた自動で作るファイルなので git restore で捨ててから pull
db push が「up to date」なのに新しい列が無いpull が失敗していて、新しいマイグレーションのファイルが届いていなかったpull し直してから db push。エラーが出たら、次のコマンドに進まない
Refresh Token Not Found別の PC でログインし直したため、ブラウザに残っていた古いログイン情報が使えなくなったログインし直せば解決（心配いらない）
5 泊の旅行に「要確認」確率を掛け算していた低い方を使うように直した
学校と渋谷が同じ「日常」になる都道府県の単位でしか場所を見ていなかったいつもの場所 / ふだん行かない場所 の滞在時間を判定材料に追加
08

理解度チェック

  1. Jev に「旅行 / 帰省 / 日帰り / 日常」の 4 択（Choice）で聞くのをやめたのはなぜ？

    答えを見る

    Choice は選択肢の並び順で答えが偏ることがある（サイコロの目を聞くと、いつも 1 つめを選んだという検証がある）。「はい / いいえ」の質問に分けて、数えられること（泊数）はコードで判断した。

  2. Jev の確率（例: 87%）を画面に大きく出さないのはなぜ？

    答えを見る

    Jev の確率は、現実の確率と一致しない（較正がずれる）ことがあるから。数字はそのまま信じず、「低いときは本人に見てもらう（要確認）」という使い方にとどめた。

  3. 正解率を出すのに「合ってる」ボタンが必要なのはなぜ？

    答えを見る

    直した件数だけでは、何件中いくつ間違えたかが分からないから。合っていたことも記録して、はじめて「確かめた件数」と「当たった件数」がそろう。

  4. 確かめる 20 件を、要確認のものから順にではなく、でたらめに選ぶのはなぜ？

    答えを見る

    要確認（Jev が迷ったもの）ばかり見ると、間違いが多いものに偏って、正解率が実際より低く出るから。

  5. 「いつもの場所」を見つけるのに、地図を 500m 四方のマスに分けるのはなぜ？

    答えを見る

    何千もの地点をすべてどうしで比べると時間がかかるから。同じマスとまわりのマスの地点とだけ比べれば、近いものだけを速く数えられる。

  6. 通学の日を Jev に聞かずにコードで「日常」と決めるのは、なぜ良いの？

    答えを見る

    答えがはっきりしているものに Jev を使う必要がなく、借りているクレジットを節約できるから。迷うものだけを Jev に任せる。
